# DURE Admin Copilot PRD

## Context

DURE currently stores operational education administration data in Supabase: workspaces, groups, courses, sessions, participants, materials, attendance records, class memos, settlements, feedback, and activity logs. Operators can inspect this data through page-specific screens, but they still need to manually connect signals across pages to understand what requires attention.

Admin Copilot v1 introduces a read-only representative operator assistant. It interprets DURE's relational operational data through a lightweight domain ontology and produces a permission-aware briefing of current operations and unresolved administrative tasks.

The first implementation should stay small. It should not introduce a separate graph database, arbitrary SQL generation, autonomous actions, or a broad chatbot platform. It should use existing service-layer patterns and return explainable, evidence-backed task recommendations.

## Product Definition

DURE Admin Copilot v1 is a read-only representative-operator copilot that summarizes the workspace's near-term operations and recommends unresolved administrative tasks with evidence and navigation targets.

### One-Sentence MVP

A representative operator can open the workspace dashboard, see a 7-day operational briefing plus unresolved administrative task recommendations, and inspect the evidence and related screen link for each recommendation without the agent changing data.

## Goals

- Give representative operators a concise operational briefing across courses, sessions, materials, attendance, feedback, and completion candidates.
- Detect unresolved administrative tasks using explicit DURE rules, not hidden LLM guesses.
- Return evidence for each recommendation: source entity type, entity id, label, reason, and related screen path.
- Keep v1 read-only. The copilot may recommend actions but must not execute mutations.
- Use DURE's service layer and permission model. The LLM must never receive raw unrestricted workspace data.
- Establish an ontology-guided retrieval structure that can later evolve into Graph RAG, RDF, Neo4j, or action execution.

## Non-Goals

- No data mutation or autonomous administrative action in v1.
- No confirmation-based action execution in v1.
- No arbitrary SQL generated by an LLM.
- No separate Neo4j, RDF store, vector database, or embedding pipeline in v1.
- No instructor or group-admin copilot in the first MVP.
- No settlement request task detection in v1.
- No participant-facing or public chatbot.
- No cross-workspace analytics.
- No replacement for existing management pages.

## Primary User

### Representative Operator

A workspace-wide `owner_admin` responsible for checking overall operations and deciding what to handle next.

Needs:

- Quickly understand near-term course/session operations.
- Find unresolved items without opening every page.
- Know why each item is being recommended.
- Jump to the right existing screen to handle it manually.
- Trust that the assistant is not changing data in the background.

## MVP Scope

### Default Briefing Window

The default briefing window is:

- Recent context: previous 7 days.
- Near-term context: today plus next 7 days.

The product may label this as `최근 7일 + 앞으로 7일`.

### Included Administrative Signals

MVP includes four task categories:

1. Pending material review.
2. Attendance-risk participants.
3. New course feedback.
4. Course completion candidates.

Settlement requests are intentionally excluded from v1.

## User Experience

### Entry Point

The recommended first UI is:

- Workspace dashboard briefing cards.
- A lightweight question input area for follow-up read-only questions.

The dashboard card should come first because the operator's core need is not always to chat, but to immediately see what needs attention.

Potential route placement:

- Primary candidate: `/workspaces/[workspaceId]/home`.
- Alternative candidate: a dedicated panel reachable from the workspace dashboard layout.

The final route can be decided during implementation, but the PRD assumes the copilot appears in the representative operator's workspace experience.

### Response Structure

Copilot output should use this structure:

1. Summary
   - Core counts and short operational overview.
2. Priority tasks
   - Highest-priority unresolved items first.
3. Evidence
   - Source data that triggered each recommendation.
4. Next actions
   - Manual action suggestion and related page link.

Example shape:

```text
운영 브리핑
- 앞으로 7일 내 예정 회차: 8개
- 확인 미정 자료: 3개
- 출석 위험 참여자: 2명
- 새 피드백: 4개
- 진행 완료 후보 수업: 1개

우선순위 태스크
1. 확인 미정 자료 검토
   - 데이터분석 입문 / 1주차 자료
   - 근거: reviewStatus = pending
   - 다음 행동: 수업 자료 화면에서 확인 처리
```

## Administrative Signal Rules

### 1. Pending Material Review

A material review task is created when:

- `materials.review_status = 'pending'`.
- `materials.upload_status = 'uploaded'`.
- The material belongs to the current workspace.
- The current user is an active representative operator for the workspace.

Recommended evidence:

- Material id.
- Material title.
- Course id and course name.
- Upload/review status.
- Created/updated timestamp.
- Related materials page href.

### 2. Attendance-Risk Participant

A participant is attendance-risk when:

- Considering the participant's most recent 3 attendance records in included sessions for a course.
- At least 2 of those 3 records have `attendance_status = 'absent'`.

Session eligibility for this signal:

- Session belongs to a course in the workspace.
- Session rollup status is `included`.
- Cancelled sessions should not count as normal attendance evidence.

Recommended evidence:

- Participant id and name.
- Course id and course name.
- Recent 3 attendance statuses.
- Session ids and dates used in the calculation.
- Related course participant or attendance page href.

Open implementation note:

- If fewer than 3 attendance records exist, v1 should not flag the participant unless the implementation explicitly documents a stricter fallback. The default PRD position is to require 3 records to avoid over-triggering.

### 3. New Course Feedback

A feedback review task is created when:

- `course_feedbacks.status = 'new'`.
- The feedback belongs to a course in the current workspace.
- The feedback is visible to representative operators.

Recommended evidence:

- Feedback id.
- Course id and course name snapshot.
- Category.
- Created timestamp.
- Short message preview.
- Related feedback page href.

### 4. Course Completion Candidate

A course is a completion candidate when:

- `courses.status = 'in_progress'`.
- The final eligible session's end datetime is in the past.

Eligible final session criteria:

- `course_sessions.rollup_status = 'included'`.
- `course_sessions.visibility_status = 'visible'`.
- `course_sessions.progress_status = 'scheduled'`.

Recommended evidence:

- Course id and course name.
- Final eligible session id.
- Final eligible session date, start time, and end time.
- Current course status.
- Related course edit or course home href.

## Briefing Summary Requirements

The briefing should include at least:

- Upcoming eligible sessions count for the next 7 days.
- Recent completed/elapsed sessions count for the previous 7 days when useful.
- Pending material review count.
- Attendance-risk participant count.
- New feedback count.
- Completion candidate course count.
- Top recommended tasks sorted by priority.

## Priority Model

v1 should use deterministic priority rules before any LLM phrasing.

Recommended priority order:

1. Attendance-risk participants.
2. Pending material reviews.
3. Course completion candidates.
4. New feedback.

Tie-breakers:

- Older unresolved items first for material review and feedback.
- More recent attendance risk evidence first for attendance-risk participants.
- Older completion candidates first for courses whose final session ended earlier.

The LLM may explain or format the result, but it must not invent extra priority signals not returned by service-layer detection.

## Permissions and Security

### Actor

v1 is restricted to representative operators:

- Current user must be authenticated.
- Current user must have an active `workspace_members` row for the workspace.
- Current member role must be `owner_admin`.

If this is not true, the service should return the existing API error style, such as:

- `AUTH_REQUIRED`
- `WORKSPACE_ACCESS_DENIED`
- `ROLE_FORBIDDEN`

### Retrieval Boundary

The copilot must retrieve only data the actor is allowed to see. Do not fetch all workspace data into the LLM and ask the model to hide unauthorized parts.

### LLM Boundary

The LLM must not:

- Generate arbitrary SQL.
- Receive service role credentials.
- Call admin client directly.
- Mutate DURE data.
- Infer private data outside the returned service result.

## Ontology-Guided Retrieval Approach

v1 should not implement a separate graph database. Instead:

- Supabase remains the source of truth.
- Existing service-layer patterns remain the authority for auth, permission, and data access.
- DURE entities and relationships are described in `docs/ontology.md`.
- Query results are normalized into graph-shaped context: focus nodes, related nodes, edges, evidence, signals, and recommended manual actions.

This can be described as ontology-guided retrieval over relational operational data. Neo4j, RDF/OWL, embeddings, and full Graph RAG are v2+ extension candidates.

## Suggested API / Service Contract

The exact implementation may evolve, but v1 should converge toward a service contract similar to this:

```ts
type GetAdminCopilotBriefingInput = {
  workspaceId: string;
  referenceDate?: string; // ISO date or datetime; defaults to now
};

type AdminCopilotBriefing = {
  window: {
    timezone: string;
    recentFrom: string;
    today: string;
    upcomingUntil: string;
  };
  summary: {
    upcomingSessionCount: number;
    recentSessionCount: number;
    pendingMaterialCount: number;
    attendanceRiskParticipantCount: number;
    newFeedbackCount: number;
    completionCandidateCount: number;
  };
  tasks: AdminCopilotTask[];
};

type AdminCopilotTask = {
  id: string;
  type:
    | 'pending_material_review'
    | 'attendance_risk_participant'
    | 'new_course_feedback'
    | 'course_completion_candidate';
  priority: 'high' | 'medium' | 'low';
  title: string;
  summary: string;
  evidence: AdminCopilotEvidence[];
  relatedHref: string;
  recommendedManualAction: string;
  createdAt?: string;
};

type AdminCopilotEvidence = {
  entityType:
    | 'course'
    | 'course_session'
    | 'participant'
    | 'material'
    | 'attendance_record'
    | 'course_feedback';
  entityId: string;
  label: string;
  reason: string;
  metadata?: Record<string, unknown>;
};
```

Recommended service file:

- `src/services/admin-copilot.ts`

Recommended validator file if input grows:

- `src/lib/validators/admin-copilot.ts`

## UI Requirements

The UI should show:

- Loading state.
- Empty state when there are no recommended tasks.
- Error state when permission or data loading fails.
- Summary cards for key counts.
- Prioritized task list.
- Evidence details per task.
- Related screen link per task.
- Explicit read-only label, such as `읽기 전용 추천입니다. 처리는 각 관리 화면에서 직접 진행해 주세요.`

## Acceptance Criteria

MVP is acceptable when:

- A representative operator can open the workspace experience and see an Admin Copilot briefing.
- The briefing uses the default window: previous 7 days plus today and next 7 days.
- The briefing includes the four v1 signal categories: pending material review, attendance-risk participants, new feedback, and course completion candidates.
- Settlement requests are not included in v1 task detection.
- Every task includes a reason and at least one evidence entity id.
- Every task includes a related DURE page href where the operator can manually inspect or handle the issue.
- Non-owner roles cannot access the v1 representative-operator copilot service.
- The implementation does not generate arbitrary SQL with an LLM.
- The implementation does not mutate data.
- The implementation passes the project verification commands relevant to the changed code.

Recommended quality targets:

- Briefing data loads in a practical dashboard time budget for normal workspace sizes.
- Task detection is deterministic and testable without calling an LLM.
- LLM usage, if added, is limited to phrasing/summarization over already permission-filtered service output.

## Manual Validation Plan

The user will perform final product validation directly. Engineering should prepare seed or local test scenarios covering:

1. Workspace with no unresolved tasks.
2. Workspace with pending uploaded materials.
3. Participant with 2 absences in the most recent 3 attendance records.
4. New course feedback.
5. In-progress course whose final included, visible, scheduled session ended in the past.
6. Non-owner active member attempting access.

## Future Extensions

v2+ candidates:

- Confirmation-based action execution.
- Group-admin scoped copilot.
- Instructor course copilot.
- Settlement request recommendations.
- Natural-language follow-up question router.
- Embedding-backed document RAG for internal docs and policy questions.
- Graph projection read model.
- Neo4j or RDF/OWL export.
- Agent audit log for recommendations and action confirmations.
