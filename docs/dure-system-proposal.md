# DURE System 기획안

- 상태: 팀 검토용 초안
- 작성일: 2026-09-13
- 대상: 사회복지 센터 프로그램 운영자
- 목표 검증 기간: 1~2개월

## 1. 기획 목적

DURE System은 종이 일지, 엑셀, Google Form 등 여러 도구에 흩어진 참여 기록을 안전하게 축적하고, 분기·연도·프로그램별 통계와 외부 제출 자료로 바꾸는 운영자 중심 시스템이다.

첫 단계의 핵심 질문은 다음과 같다.

> 어떤 참여자가 어떤 프로그램에 어느 기간 동안 얼마나 지속적으로 참여했으며, 이 근거로 다음 분기에 어떤 프로그램을 운영할 것인가?

강사의 앱 사용이나 당일 출석률 자체를 도입 성공 기준으로 삼지 않는다. 강사는 기존 종이 일지를 계속 사용할 수 있고, 운영자는 정리된 데이터를 가져와 검증·보고하는 흐름부터 사용한다.

## 2. 해결하려는 문제

센터는 분기별 약 24개 수업, 현재 이용자 약 160명, 누적 기록 대상 약 6,000명을 관리한다고 설명했다. 기존 인터뷰의 실인원 400~500명, 연인원 약 1만 명과는 집계 기간 또는 대상 범위가 다를 수 있어 재확인이 필요하다.

현재 업무의 주요 문제는 다음과 같다.

- 엑셀 전달과 수정 과정에서 수식이 깨지고 매크로가 오작동한다.
- 누적 기록이 많아질수록 파일이 복잡해지고 데이터 손상 가능성이 커진다.
- 제출 전마다 운영자가 수식과 값을 수작업으로 재검산한다.
- 종이 일지, 신청 데이터, 출석 데이터, 입금 데이터가 서로 연결되지 않는다.
- 외부 제출 자료를 만들 때 개인정보를 다시 수작업으로 제거한다.
- 일별 출석 화면만으로는 분기·연도·프로그램별 운영 판단을 하기 어렵다.

## 3. 제품 원칙

1. 같은 데이터는 한 번만 정규화해 이후 보고와 운영에서 재사용한다.
2. 원본을 바로 덮어쓰지 않고 `미리보기 → 오류 확인 → 운영자 확정`을 거친다.
3. 통계 수치는 명시된 계산 규칙으로 생성하고 근거 기록까지 역추적할 수 있게 한다.
4. 내부 원본과 외부 제출용 projection을 분리한다.
5. 개인정보 접근은 역할과 사용 목적에 따라 제한한다.
6. 강사의 디지털 입력을 강제하지 않는다.
7. AI는 검증된 수치의 표현을 돕고 계산 source of truth가 되지 않는다.
8. 임의 형식의 모든 파일을 자동 해석하려 하지 않고 합의된 업로드 형식부터 지원한다.

## 4. 사용자와 권한

| 사용자 | 주요 업무 | 기본 접근 범위 |
| --- | --- | --- |
| 대표 운영자 | 전체 데이터 가져오기, 정합성 확인, 참여자 관리, 보고서와 export 생성, 백업·복구 | 워크스페이스 전체 |
| 그룹 운영자 | 배정된 프로그램의 운영 데이터 확인과 수정 | 지정 그룹 범위. 연락처·전체 export는 기본 제외 |
| 강사 | 담당 수업의 명단과 수업에 필요한 최소 정보 확인, 선택적으로 출석·메모 입력 | 담당 수업. 전화번호·상세 주소·외부 제출 기능 제외 |
| 참여자 | 프로그램에 참여하는 운영 대상 | 로그인과 시스템 권한 없음 |

첫 MVP에서 연락처 원본 다운로드와 외부 제출 파일 생성은 대표 운영자에게만 허용한다. 센터에서 여러 운영자가 해당 업무를 수행해야 한다면 별도 export 권한을 설계한다.

## 5. 용어와 운영 구조

- `워크스페이스`: 한 센터의 최상위 데이터와 권한 경계
- `그룹`: 프로그램 기준으로 오래 유지하는 운영 단위이자 권한 범위
- `수업`: 특정 기간에 실제 운영되는 교육 과정
- `운영 기간`: 2026년 1분기처럼 신청·납부·참여 통계를 구분하는 기간
- `회차`: 특정 날짜와 시간에 진행된 수업 단위
- `참여자`: 로그인하지 않는 운영 대상 데이터
- `데이터 가져오기`: 합의된 Excel·CSV를 검증해 정규화 데이터로 저장하는 작업
- `외부 제출 자료`: 승인된 필드만 포함해 내부 원본과 별도로 생성한 파일

마포 센터에서는 그룹을 미술·체육·음악·상담 같은 프로그램 기준으로 사용하는 방향을 우선 검증한다. 분기마다 같은 그룹을 복제하지 않는다. 프로그램 분류와 실제 권한 범위가 다르면 별도 프로그램 객체를 도입한다.

## 6. MVP 사용자 흐름

```text
운영자가 합의된 Excel·CSV 준비
→ 파일 선택
→ 열과 값 형식 검사
→ 중복 참여자·알 수 없는 프로그램·오류 행 확인
→ 예상 신규·수정·제외 건수 확인
→ 운영자가 가져오기 확정
→ 분기·연도·프로그램별 보고 확인
→ 집계 수치의 근거 행 확인
→ 마스킹된 외부 제출 파일 생성
→ 생성 이력과 백업 확인
```

가져오기 미리보기 단계에서는 업무 데이터를 변경하지 않는다. 같은 파일을 다시 확정해도 데이터가 중복 반영되지 않아야 한다.

## 7. MVP 범위

### 7.1 기준 자료와 계산 계약

개발 전에 다음 자료를 비식별 형태로 확보한다.

- 기존 출석·참여 엑셀의 열 구조와 대표 오류 사례
- 실제 월별·분기별 보고서의 빈 양식 또는 비식별 예시
- 종이 출석부의 빈 양식
- 실인원·연인원·지속 참여 계산 walkthrough
- 외부 제출 허용·금지 필드와 승인자

다음 규칙을 함께 확정한다.

- 현재 이용자, 누적 이용자, 등록 인원, 실인원, 연인원의 차이
- 부분 출석, 미입력, 결석, 취소·보강 회차의 포함 방식
- 중도 등록·중단과 프로그램 이동 처리
- 동명이인, 개명, 연락처 변경 시 기존 참여자를 찾는 방법
- 월별 보고와 분기별 보고의 계산 기준 차이
- 연령대 계산 기준일과 구간

주민등록번호는 참여자 식별 키로 사용하지 않는다. 센터가 이미 사용하는 비민감 내부 번호가 있는지 먼저 확인한다.

### 7.2 데이터 가져오기

첫 버전은 출석 또는 참여 현황 파일 한 종류만 지원한다.

필수 기능:

- Excel 또는 CSV 파일 선택
- 필수 열 누락 검사
- 날짜, 상태, 프로그램명 등 값 형식 검사
- 동명이인과 중복 참여자 후보 표시
- 존재하지 않는 그룹·수업 표시
- 신규·수정·제외 예상 건수 표시
- 오류 행과 사유 목록 제공
- 운영자 확정 전 데이터 변경 금지
- 파일 hash를 이용한 중복 반영 방지
- 가져오기 batch, 수행자, 시각, 원본 행, 결과 이력

첫 코드 변경은 파일을 저장하지 않는 순수 parser·validator와 정답 fixture로 시작한다. dry-run 결과가 확정된 뒤 DB migration과 확정 저장을 구현한다.

### 7.3 참여자와 프로그램 데이터

논리적으로 다음 정보를 분리한다. 실제 테이블 구조는 샘플 파일과 권한 검토 후 확정한다.

| 정보 영역 | 예시 | 접근 |
| --- | --- | --- |
| 참여자 핵심 | 내부 식별자, 이름, 상태 | 운영자. 강사는 담당 수업의 최소 항목 |
| 보고 정보 | 성별, 생년 또는 연령대, 장애 유무 | 운영자. 승인된 항목만 export |
| 연락 정보 | 전화번호, 상세 주소 | 대표 운영자 전용 |
| 강사 안내 | 수업 지원에 꼭 필요한 주의사항 | 담당 강사. 상세 진단·연락정보 제외 |
| 운영 관계 | 그룹, 수업, 배정일, 제외 상태 | 역할별 범위 |

MVP에서는 주민등록번호와 상세 장애 유형을 새로 수집하지 않는다. 상세 장애 유형 저장이 반드시 필요하다는 근거가 생기면 목적, 접근자, 보존 기간, 수정·삭제 책임을 먼저 승인받는다.

### 7.4 분기·연도 참여 보고

기본 필터:

- 연도
- 분기
- 프로그램 또는 그룹
- 수업
- 장애 유무
- 필요시 성별과 연령대

기본 지표 후보:

- 등록 참여자 수
- 실제 참여자 수
- 총 참여 횟수
- 프로그램별 참여 추이
- 장애인·비장애인 참여 비율
- 성별·연령대별 분포
- 여러 기간에 걸친 지속 참여 현황

각 지표의 정확한 계산식은 기준 보고서와 함께 확정한다. 특히 `실제 참여자`, `총 참여 횟수`, `지속 참여`는 현재 용어만으로 계산하지 않는다.

모든 집계는 수치의 근거가 된 참여자·수업·회차·출석 기록을 운영자가 확인할 수 있어야 한다. AI가 원본 집계 수치를 생성하거나 수정하지 않는다.

### 7.5 마스킹된 외부 제출 자료

외부 제출 파일은 내부 조회 데이터에서 임의로 열을 숨기는 방식이 아니라 별도 export projection으로 생성한다.

기본 허용 후보:

- 이름
- 성별
- 연령대
- 장애 유무
- 프로그램과 기간별 참여 수치

기본 금지:

- 전화번호
- 상세 주소
- 주민등록번호
- 상세 장애 유형
- 수업 운영과 제출 목적에 필요하지 않은 개인 메모
- 원본 파일 경로와 내부 식별용 metadata

이름도 개인 식별 정보이므로 실제 제출 양식과 수령 기관의 요구가 확인된 경우에만 포함한다.

export에는 생성자, 생성 시각, 적용 기간, 필터, 양식 버전, 결과 파일 정보를 기록한다. 파일을 다시 생성해도 당시 사용한 조건을 확인할 수 있어야 한다.

### 7.6 Windows 로컬 운영

최종 제공 형태는 Windows 로컬 애플리케이션을 목표로 한다. 현재 DURE는 Next.js와 Supabase 기반 웹 앱이므로 로컬 전환은 별도 기술 검증이 필요하다.

필수 운영 조건:

- 인터넷이 없어도 핵심 조회·가져오기·보고 기능 사용
- 로컬 데이터 암호화
- 앱 로그인과 역할별 projection
- 원본 파일과 생성 파일의 명확한 보관 위치
- 자동 백업과 수동 백업
- 새 PC에서 복구할 수 있는 절차
- 앱 버전과 데이터 schema migration 관리
- 오류가 발생해도 기존 데이터를 훼손하지 않는 복구 경로

기술 스택을 선택하기 전에 다음을 확인한다.

- 실제 사용할 Windows 버전
- 업무에 사용할 PC 수
- 여러 운영자의 동시 편집 필요 여부
- 센터 내부 공유 폴더 또는 NAS 사용 가능 여부
- 백업 책임자와 허용 저장 위치
- PC 교체 시 허용 가능한 복구 시간
- 기존 Supabase 데이터를 이관할지, 웹 앱과 병행할지

여러 PC에서 동시에 같은 데이터를 수정해야 한다면 단일 PC 로컬 DB만으로는 요구를 충족하지 못한다. 이 경우 센터 내부 서버 또는 제한된 원격 동기화 구조를 다시 검토한다.

## 8. 화면 구성

### 8.1 홈

- 현재 선택한 연도와 분기
- 프로그램별 참여 현황
- 가져오기 오류 또는 미확정 batch
- 최근 생성한 보고서
- 백업 상태

일별 출석 그래프는 기본 화면의 중심에서 제외하고 필요한 경우 상세 근거로 제공한다.

### 8.2 데이터 가져오기

- 파일 선택
- 업로드 형식과 양식 버전 표시
- 미리보기 표
- 오류·경고 필터
- 신규·수정·제외 예상 건수
- 가져오기 확정
- 과거 가져오기 이력

### 8.3 참여자 관리

- 이름 또는 내부 번호 검색
- 프로그램·상태·기간 필터
- 기본 정보와 프로그램 참여 이력
- 동명이인 구분과 중복 병합 후보
- 운영자 전용 연락 정보

중복 병합은 출석·신청·납부 기록에 영향을 줄 수 있으므로 MVP에서는 자동 실행하지 않고 후보만 제시한다.

### 8.4 보고서

- 연도·분기 선택
- 프로그램 비교
- 참여 추이
- 장애 유무 비율
- 필요시 성별·연령대 분포
- 집계 근거 보기
- 외부 제출 파일 생성

### 8.5 설정과 백업

- 현재 앱과 데이터 schema 버전
- 사용자와 권한
- 업로드 양식 버전
- 자동 백업 위치와 최근 성공 시각
- 수동 백업과 복구
- export 이력

## 9. MVP 이후 범위

### 신청·대기자 관리

- Google Form 결과 가져오기 또는 단순 신청서
- `신청 → 검토 → 선정 → 대기 → 등록` 상태
- 기존 참여자와 신규 신청자 구분
- 프로그램 정원과 중복 신청 검증
- 참여자 마스터로 전환한 이력

### 이용료 관리

- 입금 내역 Excel 업로드
- 참여자 자동 매칭 후보와 수동 확인
- 분기별 납부·미납·확인 필요 상태
- 수정 이력
- 영수증 생성·보관·전달 범위

### 문자 발송 이력

- 대상자와 발송 사유
- 발송 날짜
- 성공·실패·미발송 상태
- 참여자별 발송 이력
- 전화번호를 직접 노출하지 않는 운영자 발송 흐름

실제 문자 발송 연결은 수신 동의, 업체, 비용, 운영자 승인, 실패와 재시도 기준을 정한 뒤 구현한다.

### AI 보고 인터페이스

- 여러 AI 제공자를 교체할 수 있는 adapter
- 검증된 집계 데이터만 전달
- 표·그래프·설명문 초안 생성
- 사용한 기간·필터·수치 근거 표시
- API 키의 안전한 로컬 보관

실제 참여자 행이나 연락처를 외부 AI에 전달하는 기능은 기본 범위에서 제외한다.

## 10. 구현 일정 제안

실제 파일과 보고 규칙이 제때 제공된다는 전제의 6주 계획이다.

| 기간 | 구현·검증 내용 | 완료 기준 |
| --- | --- | --- |
| 1주차 | 비식별 파일·보고 양식 분석, 계산 계약, 목업, Windows 운영 조건 확인 | 입력 열, 정답 수치, 개인정보 경계, 첫 화면 흐름 합의 |
| 2주차 | import parser·validator와 정답 fixture | 오류·중복·정상 파일의 dry-run 결과 일치 |
| 3주차 | import batch와 확정 저장, 참여자 식별·그룹/수업 연결 | 중복 반영 없이 가져오고 결과를 역추적 가능 |
| 4주차 | 분기·연도·프로그램별 집계와 보고 화면 | 기준 fixture의 모든 집계가 정답과 일치 |
| 5주차 | 마스킹 export와 권한·감사 이력 | 금지 필드가 없고 허용된 운영자만 생성 가능 |
| 6주차 | Windows 패키징, 백업·복구, 센터 파일 리허설 | 새 PC 복구 후 같은 보고 결과 재생성 |

기준 자료 제공이나 계산 규칙 합의가 늦어지면 기능 수를 늘리지 않고 해당 단계의 검증 기간을 늘린다.

## 11. 성공 기준

### 데이터 신뢰성

- 기준 파일의 정상·오류·중복 행을 합의한 결과로 분류한다.
- 같은 파일을 반복 확정해도 데이터가 중복되지 않는다.
- 보고서의 모든 수치가 기준 정답과 일치한다.
- 운영자가 각 수치에서 근거 기록을 찾을 수 있다.

### 개인정보

- 강사 화면과 query 결과에 전화번호가 포함되지 않는다.
- 외부 제출 파일과 metadata에 금지 필드가 포함되지 않는다.
- 대표 운영자가 아닌 사용자는 원본 다운로드와 export를 실행할 수 없다.
- 실제 참여자 데이터 없이도 자동 테스트를 실행할 수 있다.

### 운영 가능성

- 운영자가 설명 없이 파일 선택, 오류 확인, 확정, 보고서 생성을 완료할 수 있다.
- 앱 종료나 가져오기 실패가 기존 데이터를 훼손하지 않는다.
- 백업 파일을 새 환경에 복구해 같은 보고 결과를 재생성할 수 있다.
- 사용한 업로드 양식과 보고 양식의 버전을 확인할 수 있다.

## 12. 주요 위험과 대응

| 위험 | 영향 | 대응 |
| --- | --- | --- |
| 실제 엑셀 형식이 계속 변함 | import 실패와 유지보수 증가 | 양식 버전 관리, 명시적 열 매핑, 오류 미리보기 |
| 이름만으로 참여자를 매칭 | 동명이인과 잘못된 기록 연결 | 비민감 내부 식별자 도입, 애매한 경우 운영자 확인 |
| 계산 규칙이 담당자마다 다름 | 보고 수치 불신 | 정답 fixture와 계산 계약을 먼저 승인 |
| 프로그램 분류와 권한 그룹이 다름 | 잘못된 접근 또는 집계 | 사례 확인 후 별도 프로그램 객체 검토 |
| 단일 PC 고장 | 전체 데이터 손실 | 암호화 백업, 복구 rehearsal, 책임자 지정 |
| 여러 PC 동시 수정 | 충돌과 데이터 분기 | 동시 사용 확인 후 내부 서버·동기화 구조 결정 |
| AI가 잘못된 수치를 생성 | 외부 보고 오류 | deterministic 집계만 source of truth로 사용 |
| export에서 개인정보 누출 | 참여자 피해와 기관 책임 | allowlist projection, 권한 검사, 자동 금지 필드 테스트 |

- 임의 형식의 모든 엑셀을 자동 변환하는 범용 AI import
- 주민등록번호와 상세 장애 유형의 신규 수집

## 14. 다음 회의에서 확정할 항목

다음 항목이 정해져야 첫 MVP를 구현 계약으로 전환할 수 있다.

1. 첫 import 대상으로 사용할 파일 한 종류와 필수 열
2. 첫 output으로 만들 보고서 한 종류와 필수 표
3. 실인원·연인원·지속 참여의 계산식
4. 기존 참여자를 구분할 내부 식별자
5. 외부 제출 허용 필드와 최종 승인자
6. 프로그램과 그룹이 같은 범위인지
7. Windows PC 수와 동시 사용 여부
8. 백업 위치, 책임자, 복구 목표
9. 기존 Supabase 웹 앱의 이관·병행·종료 방향
10. 6주 MVP의 센터 검증 담당자와 검토 일정

## 15. 첫 실행 항목

첫 작업은 화면이나 DB부터 만드는 것이 아니다. 개인정보를 제거한 실제 파일의 열 구조와 보고서 한 종류를 기준으로 다음 산출물을 만든다.

1. `입력 열 → DURE 객체·필드` 매핑표
2. 정상 행, 오류 행, 동명이인, 중복 파일을 포함한 작은 합성 fixture
3. 실인원·연인원·기간별 참여의 기대 결과표
4. 외부 제출 허용·금지 필드표
5. 데이터 저장 없이 결과만 보여주는 import dry-run 계약

이 다섯 가지가 승인되면 parser·validator 구현을 시작하고, 그 결과를 기준으로 DB와 Windows 기술 선택을 구체화한다.
