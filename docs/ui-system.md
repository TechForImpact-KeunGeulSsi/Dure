# DURE UI System & Alignment Contract

## 목적

이 문서는 DURE의 현재 제품 계약에 맞춰 UI/UX를 일관되게 구현하기 위한 기준이다. 화면별 데이터·권한·용어 계약을 새로 정의하지 않으며, `docs/context.md`, `docs/api-spec.md`, `docs/architecture.md`를 시각·상호작용 규칙으로 연결한다.

페이지 구현자는 이 문서의 규칙을 적용하되, 화면의 query/action, DTO, enum, 권한과 오류 계약은 기존 기준 문서를 우선한다.

## 현재 alignment 범위

### 집중할 기능

- 워크스페이스 대시보드
- 캘린더
- 그룹·참여자·수업 관리
- 운영자·강사 관리
- 운영자 수업 상세·자료·참여자 현황
- 강사 수업 홈·자료·출석부·수업 메모
- 로그인·회원가입·워크스페이스 생성 등 인증/온보딩 진입 흐름

### 이번 단계에서 제외할 기능

- 종료된 공개 카탈로그·공개 수업 상세·피드백 입력 화면
- 종료된 정산·지급 화면
- 현재 제품 범위에서 제거된 Copilot 화면

위 기능의 레거시 DB 행과 Storage 객체는 보존한다. UI alignment를 이유로 데이터를 삭제하거나 migration을 변경하지 않는다.

### 1차 구현 경계

첫 alignment 단계는 색상, 타이포그래피, 간격, 표면, 공통 컴포넌트, 상태 표현, 반응형 레이아웃과 UI 카피에 한정한다. API, service, validator, DB, RLS, Storage 권한은 별도 요구가 없는 한 변경하지 않는다.

## 제품 UI 방향

### 마포 센터 도입 원칙

- 첫 사용자는 운영자이며, 기본 작업 환경은 Windows 데스크톱이다.
- 큰 글자와 명확한 대비, 익숙한 표 구조, 한 화면의 단일 주요 action을 우선한다.
- 가져오기는 `파일 선택 → 미리보기 → 오류 확인 → 확정`의 짧은 단계로 제공하고 저장 전에 반영 건수와 제외 사유를 보여준다.
- 보고 화면의 기본 시간 단위는 분기와 연도다. 일별 정보는 원인을 확인하는 상세 근거로 내려간다.
- 강사 화면은 선택 기능으로 유지하며 마포 센터 MVP의 성공 조건에 강사 앱 입력률을 넣지 않는다.
- 개인정보 필드는 역할에 따라 UI에서 가리는 것만으로 끝내지 않고 query·export projection에서 제외한다.

### 운영 화면

DURE의 인증된 화면은 마케팅 페이지보다 운영 도구에 가깝다.

- 업무 상태와 다음 action이 장식보다 먼저 보인다.
- 흰색 표면, 차분한 네이비 본문, 제한적인 블루 action을 기본으로 한다.
- 성공·주의·위험 색상은 상태 의미가 있을 때만 사용한다.
- 카드와 테두리는 정보를 묶거나 상호작용 영역을 구분할 때만 사용한다.
- 한 화면에 여러 개의 경쟁하는 강조색, 장식용 gradient, 의미 없는 아이콘을 추가하지 않는다.
- 제목과 라벨만 훑어도 현재 범위·상태·가능한 action을 이해할 수 있어야 한다.

### 인증·랜딩 화면

로그인·회원가입·랜딩은 브랜드 진입 화면으로 별도 표현을 허용한다. 다만 운영 화면의 용어, primary 색상, focus 접근성, 버튼 의미와 충돌하지 않아야 한다. 인증 화면의 장식 스타일을 운영 화면에 복사하지 않는다.

## UI 카피와 AI 작업 제한

### 기본 원칙

제품 요구사항, 기존 계약, 오류 처리, 접근성에 필요한 문구만 UI에 둔다. AI가 화면을 해설하거나 자신의 작업을 설명하기 위한 문구는 제품 기능이 아니므로 추가하지 않는다.

### 허용

- `수업 자료`, `참여자 현황`, `저장`, `취소`처럼 업무 대상을 명확히 하는 라벨과 action
- `진행 중`, `확인 미정`, `부분 출석`처럼 계약에 정의된 상태
- `이메일을 입력해 주세요`, `필수 입력입니다`처럼 입력·검증에 필요한 안내
- 저장 성공, 권한 없음, 충돌, 삭제 전 확인처럼 실제 결과와 위험을 알려야 하는 문구
- 동작과 의미를 짧게 설명하는 `aria-label` 및 screen-reader 전용 텍스트

### 금지

다음 문구를 제품 계약에 명시적으로 요구하지 않는 한 새로 추가하지 않는다.

- 화면의 목적이나 설계 의도를 설명하는 문장
- 구현 과정, 에이전트 판단, AI 사용 여부를 설명하는 문장
- `AI가 분석했습니다`, `이 화면에서 쉽게 확인할 수 있어요` 같은 해설·홍보성 문구
- 기능을 꾸미기 위한 부제, callout, helper text, tooltip, badge
- 운영자가 이미 이해할 업무를 다시 설명하는 긴 문장이나 단계 안내
- `주석`, `참고`, `팁`, `다음 단계`를 명분으로 한 비기능성 카피

구현자에게 필요한 설명은 코드 주석, 현재 문서, 리뷰에 기록한다. 화면에 보이는 문구가 필요한지 확실하지 않으면 추가하지 않고 먼저 확인한다.

## 토큰 기준

현재 [`src/app/globals.css`](../src/app/globals.css)의 `@theme` 토큰을 단일 출발점으로 사용한다. 운영 화면에서 새 색상·radius·shadow를 직접 만들지 않는다.

| 영역 | 기준 |
| --- | --- |
| 본문 | `--color-foreground`, `--color-muted-foreground` |
| 페이지·보조 표면 | `--color-background`, `--color-muted`, `--color-card` |
| 경계·입력 | `--color-border`, `--color-input` |
| 주요 action·focus | `--color-primary`, `--color-ring` |
| 위험 action | `--color-destructive` |
| radius | `--radius-sm`, `--radius-md`, `--radius-lg` |
| 서체 | `--font-sans`와 현재 Pretendard 우선순위 |

필요한 의미 토큰은 먼저 `globals.css`에 추가하고, 컴포넌트에서는 의미 토큰을 사용한다. `gray-*`, `slate-*`, `blue-*` 등의 직접 사용은 기존 예외를 점진적으로 줄이며, 출석 상태의 색상·패턴처럼 의미가 있는 도메인 표현은 예외로 문서화한다.

## 공통 컴포넌트 계약

- `Button`: `primary`, `secondary`, `outline`, `ghost`, `destructive`의 의미를 유지한다. 한 영역에는 primary action을 하나만 둔다.
- `Input`, `Select`, `Textarea`: 높이, border, placeholder, focus, disabled, 오류 표현을 동일하게 유지한다.
- `Badge`: 상태를 짧게 표시한다. 설명문을 넣는 용도로 사용하지 않는다.
- `Table`: 검색·필터·pagination·empty/error 상태와 함께 사용하는 업무 목록 표면이다.
- `NavTabs`: route 이동용이다. `Tabs`: 한 화면 안의 상태 전환용이다. 기술 구현은 달라도 시각 계약은 같게 유지한다.
- `Dialog`: 제목, 본문, footer, 취소·확인 action 순서를 일정하게 유지한다.
- `EmptyState`, `LoadingState`, `ErrorState`: 같은 페이지 구조 안에서 상태만 바꿔도 사용자가 맥락을 잃지 않게 한다.

`Card`는 모든 영역의 기본 wrapper가 아니다. 정보 묶음이나 상호작용 영역에 필요할 때만 사용하고, 단순한 목록·섹션은 표면과 구분선만으로 구성할 수 있다.

## 표준 페이지 패턴

### 운영 대시보드

`페이지 제목 → 날짜/범위 → 필터 → 요약 상태 → 주 작업 표면 → 상세 이동` 순서를 기본으로 한다. 출석 대시보드는 `getAttendanceDashboard` 계약의 날짜, 수업 다중 선택, 회차 상태, 참여자 누적 출석률을 우선 표현한다.

마포 센터 목표 보고 화면은 `운영 기간 → 프로그램 → 인구통계 필터 → 참여 요약·추이 → 근거 기록 → 마스킹 export` 순서를 사용한다. 현재 출석 대시보드를 이 목표 화면으로 변경하는 시점은 집계 계약과 기준 데이터가 확정된 뒤다.

### 관리 목록

`페이지 제목·primary action → 검색/필터 → 테이블 → pagination → empty/error` 순서를 기본으로 한다. 테이블 행에 설명성 문장을 덧붙이지 않는다.

### 수업 상세

`breadcrumb → 수업명·상태 → route tabs → 현재 작업 표면` 순서를 기본으로 한다. 운영자와 강사 화면의 탭은 역할에 맞는 항목만 노출한다.

### 폼·dialog

필드 label은 입력 대상 자체를 말하고, helper text는 validation·범위·주의에 필요할 때만 사용한다. 저장 결과는 toast 또는 명확한 상태 변화로 한 번만 알린다.

## 역할·용어 기준

- 역할은 `대표 운영자`, `그룹 운영자`, `강사`로 표시한다.
- 운영 대상은 `참여자`, 로그인 가능한 사용자는 `멤버` 또는 역할명으로 구분한다.
- `그룹`, `수업`, `참여자`, `회차`, `출석부`, `수업 메모`, `확인 미정`, `확인됨`, `부분 출석`은 `docs/context.md`의 표현을 따른다.
- 버튼 노출은 UX 보조일 뿐이다. 실제 권한은 service/action과 RLS에서 재검증한다.
- 강사 화면에 일반 일정이나 운영자 전용 데이터를 섞지 않는다.

## 적용 순서

1. 이 문서와 화면별 audit matrix를 먼저 확정한다.
2. `globals.css` 토큰과 `Button`, `Input`, `Select`, `Dialog`, `Card`, `Table`, `Tabs`, `Badge`, 상태 컴포넌트를 정렬한다.
3. `Sidebar`, `Header`, dashboard shell을 정렬한다.
4. 대시보드, 관리 목록, 수업 상세, 강사 출석부를 기준 화면으로 만든다.
5. 자료·메모·멤버·캘린더·온보딩 화면을 기준 화면에 맞춰 점진적으로 이식한다.
6. 인증·랜딩은 별도 brand mode로 검토한다.

한 번에 모든 페이지의 className을 기계적으로 치환하지 않는다. 두 개 이상의 화면에서 같은 구조가 반복될 때만 작은 공통 컴포넌트를 추출한다.

## 완료 기준

- 새 운영 UI가 이 문서의 토큰과 공통 컴포넌트를 사용한다.
- 같은 의미의 action, 상태, 오류, empty, focus 표현이 화면마다 다르지 않다.
- visible copy가 실제 업무·상태·결과·접근성에 필요한 문구만 포함한다.
- AI·에이전트·설계 의도·구현 과정에 대한 불필요한 문구가 UI에 없다.
- 데스크톱과 모바일에서 정보 우선순위와 가로 overflow가 검증된다.
- owner, group_admin, instructor의 노출·action이 기존 화면 계약과 일치한다.
- `npm run typecheck`, `npm run lint`, `npm run build`와 변경 범위의 관련 테스트를 실행한다.
- UI 변경만으로 끝나는 단계에서는 API, DB, RLS, Storage 동작이 불필요하게 변하지 않는다.
